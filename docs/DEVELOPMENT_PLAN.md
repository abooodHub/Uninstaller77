# خطة تطوير وإصلاح Uninstaller 77

تاريخ خط الأساس: 2026-11-06

هذه الخطة تحول عبارة «حل كل العيوب» إلى عملية يمكن قياسها والتحقق منها. لا يمكن لأي مشروع برمجي أن يثبت رياضيًا عدم وجود أي عيب مجهول، لذلك معيار الإكمال هنا هو: لا توجد عيوب حرجة أو عالية معروفة، وكل مسار خطر له اختبار فشل سابق واختبار نجاح بعد الإصلاح، وجميع بوابات الإصدار تمر على الحزمة الفعلية.

## 2. مستويات الأولوية

- **P0 — حرج:** قد يحذف أو يشغّل هدفًا غير مصرح به، يفقد بيانات المستخدم، يتجاوز حدود الأمر، أو يعلن نجاحًا كاذبًا.
- **P1 — عالٍ:** تعطل، فساد سجل/قاعدة بيانات، سباق عمليات، فشل ترقية/إزالة، أو واجهة تعلق دون تشخيص قابل للاسترجاع.
- **P2 — متوسط:** دين تقني يزيد احتمال العيوب، نقص وصول/أداء، أو غياب أتمتة تحقق مهمة.
- **P3 — تحسين:** تنظيم، تقليل تكرار، وضوح التوثيق، أو تحسين تجربة لا يغير صحة الإزالة.

لا يبدأ إصدار جديد مع P0 أو P1 مفتوح. لا يُغلق بند إلا بدليل اختبار محفوظ.

## 3. ثوابت الأمان التي لا يجوز كسرها

1. لا يُشغّل أمر إزالة إلا للتطبيق الذي أكّد المستخدم هويته الحالية.
2. تغيّر التسجيل أو المسار أو وسيطات الأمر بعد التأكيد يوقف العملية بدل استخدام بيانات قديمة.
3. اختفاء التسجيل قبل التشغيل هو تخطٍ محايد، وليس نجاح إزالة مصطنعًا.
4. خروج العملية لا يكفي وحده لإثبات الإزالة؛ يجب الاحتفاظ بالملاحظة والرمز والأدلة منفصلة.
5. لا يُحذف ملف أو مجلد دائمًا إلا بعد إعادة التحقق من الهوية والمسار وغياب reparse points.
6. WebView يقبل أوامر allowlist صريحة فقط، بمخطط payload مغلق ومصدر موثوق.
7. فشل الحماية أو السجل أو التشخيص لا يُخفى، ولا يغير نتيجة المحرك الأصلية.
8. ترقية قاعدة البيانات لا تسقط الجداول أو السجلات التاريخية، ولها نسخة رجوع قبل أي تغيير كبير.
9. المثبّت لا يرقّي payload أو Runtime غير متحقق من التجزئة/التوقيع/الإصدار.
10. اختبارات القبول لا تلمس تطبيقات أو ملفات أو ملفات متصفح حقيقية للمستخدم.

## 4. المرحلة A — إغلاق P0/P1 في المحرك والأمان

### A1. دورة حياة WebView والأحداث غير المتزامنة

- مراجعة `OnBrowserProcessFailed` و`OnWebMessageReceived` كحدود `async void` وحصر كل استثناء داخل مسار تشخيصي.
- منع سباقات: إغلاق النافذة أثناء التهيئة، وصول رسالة من Core قديم، وفشل ProcessFailed متكرر أثناء الاستعادة.
- إضافة اختبارات: فشلان متزامنان، إغلاق أثناء `CreateAsync`، رسالة متأخرة من browser سابق، وفشل إعادة الإنشاء.
- **مكتمل عندما:** لا crash ولا duplicate handler ولا إرسال حالة إلى Core قديم، واختبار Native UI يمر مرتين متتاليتين.

### A2. الطابور، الإيقاف، والتعافي من الانهيار

- اختبار journal عند الانقطاع في كل نقطة: قبل launch، بعد launch، بعد exit، بعد التحقق، وأثناء كتابة History.
- جعل replay idempotent؛ إعادة التشغيل لا تعيد إزالة عنصر ولا تنسب نجاحًا بلا دليل.
- اختبار إيقاف يدوي متزامن مع review/timeout وخروج worker.
- **مكتمل عندما:** كل حالة نهائية finite، ولا عنصر تالٍ يبدأ دون تأكيد جديد، ولا سجل تاريخ مكرر.

### A3. ملكية Registry/MSI/MSIX ومنع TOCTOU

- property/fuzz tests لصيغ الاقتباس، GUIDs، `%ENV%`، MSI per-user/per-machine، مسارات UNC، والوسيطات الطويلة.
- إعادة قراءة الهوية مباشرة قبل التشغيل ومقارنة التسجيل/الناشر/المسار/الوسيطات المؤكدة.
- اختبار تغيير المفتاح أو الملف بين preflight وlaunch.
- **مكتمل عندما:** كل اختلاف يرفض قبل إنشاء العملية، ولا تستخدم heuristics الاسم وحده كملكية.

### A4. الملفات والبقايا والحذف الدائم

- اختبارات symlink/junction/reparse، case changes، hard links، تبديل الملف بعد المراجعة، locked files، والمسارات الطويلة.
- فصل نتائج `deleted / retained / changed / inaccessible` دون دمجها في نجاح عام.
- **مكتمل عندما:** لا حذف خارج الجذر المسجل، وكل رفض يحتفظ بالمسار والسبب دون كشف بيانات زائدة.

### A5. Web bridge وJSON

- fuzzing للأحجام والعمق، duplicate properties، Unicode غير صالح، أرقام overflow، payloads إضافية، ورسائل من origin غير موثوق.
- إبقاء `DispatchAsync` allowlist صريحًا؛ لا reflection ولا dispatch ديناميكي.
- حد موحد لحجم الرسالة وزمن التنفيذ، واستجابة خطأ آمنة لا تتضمن stack trace.
- **مكتمل عندما:** لا عملية غير مصرح بها تصل إلى ViewModel، واختبارات البروتوكول والمحرك تغطي كل op متاح ومرفوض.

### A6. قاعدة البيانات والتاريخ

- إضافة schema version صريح بدل الاعتماد فقط على اكتشاف الأعمدة.
- نسخة احتياطية ذرية قبل ترقية SQLite الكبرى، واختبار rollback لملف قديم/تالف/مقفول.
- اختبارات concurrent readers/writers، disk full، corruption، وملفات WAL/SHM.
- **مكتمل عندما:** لا فقد تاريخ، وفتح نسخة قديمة ينتج نفس السجلات، والفشل ينشئ recovery DB مع إبقاء الأصل.

## 5. المرحلة B — الاعتمادات وسلسلة التوريد

1. ترقية `Microsoft.Data.Sqlite` من 8 إلى 10 في دفعة منفصلة، مع قاعدة بيانات fixture لكل schema تاريخي.
2. توحيد نسخ NuGet في `Directory.Packages.props` ومنع اختلاف التطبيق والاختبارات.
3. تفعيل `packages.lock.json` وlocked restore في CI، مع إبقاء `package-lock.json` المصدر الوحيد لـnpm.
4. فحص `dotnet package list --vulnerable` و`npm audit` ومنع High/Critical.
5. إضافة SBOM للحزمة النهائية وتسجيل SHA-256 لكل dependency/runtime أساسي.
6. فرض حد WebView2 Runtime الأدنى في المثبّت قبل تبني أي API تتطلبه، مع اختبار Runtime قديم وEvergreen محجوب.

**بوابة المرحلة:** restore مقفول وقابل للتكرار، فحص ثغرات نظيف، ProductIntegrity والحزمة وVM كلها ناجحة.

الحالة الحالية: رُقّي `Microsoft.Data.Sqlite` إلى 10.0.14، ووُحّدت نسخ NuGet، وثُبتت ملفات القفل وlocked restore، وأصبحت نتائج High/Critical فاشلة في CI. فحص NuGet وnpm الحالي نظيف، ويُنشأ CycloneDX SBOM من الأقفال وتُربط تجزئته ببيان الإصدار. تبقى بوابة VM والحزمة الموقعة ضمن المرحلة F.

## 6. المرحلة C — إعادة تنظيم الكود دون تغيير السلوك

### C1. الواجهة المضيفة WPF/WebView

- إبقاء ملفات `State` و`Observers` المنفصلة الحالية.
- تقسيم handlers الكبيرة إلى partials حسب المجال: inventory، queue، history، settings، وcontrol center.
- إبقاء parsing والتحقق داخل طبقة البروتوكول، والتنفيذ داخل services/ViewModels.

### C2. AppListViewModel

- فصل inventory، queue، residual review/cleanup، unregistered apps، والحوار إلى وحدات صغيرة ذات واجهات واضحة.
- نقل orchestration القابل للاختبار خارج properties المرئية، مع عدم كسر binding names.
- توحيد cancellation والتقدم وحالات busy/error في state machine محددة.

### C3. الخدمات

- واجهات صغيرة لنظام الملفات، Registry، process launcher، clock، وdatabase لتسهيل اختبارات race/failure.
- result types معرفة بدل الاعتماد على نصوص الاستثناء للتصنيف.
- تصنيف catch blocks: متوقع ومُشخّص، best-effort موثّق، أو خطأ يجب رفعه. يمنع `catch {}` غير المبرر.

### C4. الاختبارات

- تقسيم `TestRunnerService.cs` الكبير حسب المجال، مع fixture ownership helper موحد.
- لا حذف `tests/retired/Engineering` حتى تُنقل كل العقود الحية وتثبت تغطيتها.

**بوابة المرحلة:** لا تغيير في JSON أو أسماء binding أو نتائج المحرك؛ diff سلوكي صفر، وبناء warnings-as-errors.

الحالة الحالية: فُصل `WebMainWindow.Bridge.cs` عن دورة حياة النافذة، وفُصلت مسؤوليات العرض والحوارات في `AppListViewModel`، مع بقاء العقود وأسماء الربط ثابتة. إعادة البناء النظيفة، 194 اختبار محرك، و39 اختبار سلامة منتج كلها ناجحة. يستمر التفكيك الأعمق للمكونات والخدمات كتحسين P2 تدريجي، لا كشرط لإطلاق إصلاحات الأمان المثبتة.

## 7. المرحلة D — React/CSS والوصول والأداء

1. تقسيم `App.tsx` إلى صفحات ومكونات: Programs، Queue، Residual Review، Browsers، Control Center، History، Settings.
2. تعريف types لعقد host في ملف مستقل وتوليد/مقارنة fixtures مع C# DTOs.
3. تقسيم `desktop.css` إلى tokens/layout/components/pages مع الحفاظ على ترتيب cascade باختبارات render.
4. إضافة Error Boundary وحالة واضحة لفشل host/state/version mismatch.
5. تدقيق WCAG: لوحة المفاتيح، focus trap/restore، أسماء ARIA، contrast، screen reader، reduce motion.
6. تدقيق العربية: RTL، الأرقام والمسارات LTR، التفاف النص، تكبير 200–400%، وأحجام 1000x650 و1320x820.
7. ميزانية أداء: أول render، حجم JS/CSS، 1000 تطبيق، 10,000 سجل تاريخ، وذاكرة WebView بعد الاستعادة.

**بوابة المرحلة:** lint + 42 contracts الحالية + SSR + اختبارات وصول + native resize، دون نمو غير مبرر للحزمة.

الحالة الحالية: نُقل عقد المضيف إلى `host-contract.ts`، وأضيف Error Boundary ثنائي اللغة، وحجز/استعادة التركيز للحوارات والأدراج، وعقود دلالات ARIA. نجحت 42 عقود React و92 عقد SSR وlint بلا تحذيرات. ميزانية الحزمة الآلية ناجحة، واختبار القائمة الافتراضية يغطي 10,000 صف. يبقى تدقيق native resize والتكبير وقارئ الشاشة داخل بيئة سطح مكتب/VM ضمن بوابة الإصدار.

## 8. المرحلة E — CI والتحليل الأمني

- إضافة `timeout-minutes` و`concurrency` لمنع runs عالقة أو متداخلة.
- تفعيل format/analyzers، CodeQL، dependency review، وفحص أسرار دون رفع بيانات المستخدم.
- قياس coverage للمنطق الصرف فقط، والبدء بخط أساس ثم رفع الحد تدريجيًا؛ لا استخدام coverage كبديل لاختبارات المخاطر.
- رفع artifacts مختصرة ومنقحة: summaries وresult.json فقط، لا قواعد بيانات أو سجلات جهاز خام.
- تشغيل engine desktop suite وNative UI على runner داخلي/VM مصرح، مع بقاء hosted CI غير مدعٍ لاختبارات لم ينفذها.

الحالة الحالية: أضيفت بوابة CodeQL مثبتة بالإصدار لـC# وTypeScript، ومراجعة dependency changes على طلبات الدمج، وتحليل .NET وبناء deterministic، وقواعد reliability محددة مع warnings-as-errors. تبقى إضافة runner داخلي وقياس coverage التدريجي؛ لا تُرفع أدلة الجهاز الخام في CI.

## 9. المرحلة F — المثبّت والإصدار الحقيقي

مصفوفة القبول الإلزامية داخل VM قابلة للرمي:

- تثبيت نظيف: Runtime موجود / غير موجود / قديم / offline.
- مستخدم عادي، رفض UAC، restart pending، مساحة منخفضة، وملفات مقفلة.
- ترقية من كل إصدار عام مدعوم، repair، uninstall، ثم reinstall.
- Windows x64 المدعوم، لغة عربية/إنجليزية للتطبيق، وحساب جديد وحساب به بيانات سابقة.
- التحقق من الاختصارات، التسجيل، payload، WebView startup، History، وبقاء sentinels خارج مجلد المنتج.
- توقيع EXE/DLL/Setup والتحقق منه بعد البناء؛ لا نشر unsigned production artifact.
- الاحتفاظ بالمثبت الحالي وrollback حتى نجاح المصفوفة وتطابق manifest/SHA256/SBOM.

**بوابة الإصدار:** Package 50/50، Identity/manifest 25/25، Signing policy، Native UI، InstallerAcceptance، وترقية/إزالة ناجحة دون فقد بيانات.

الحالة الحالية: بُني مرشح ذاتي الاحتواء ومعزول في `_build/candidate-20261106` من المصدر الحالي دون استبدال `dist`. نجحت هوية الحزمة وmanifest/SBOM (25/25)، preflight primitives (7/7)، Inno payload preflight، وسياسة التوقيع (5/5). المرشح غير موقع ومخصص للاختبار فقط؛ التوقيع الحقيقي ومصفوفة VM ما زالا شرطين مانعين للنشر.

## 10. المرحلة G — التنظيف والأدلة والصيانة

1. معيار `result.json` موحد: suite، status، started/completed UTC، version، commit، counts، sanitized paths، وretention class.
2. الاحتفاظ تلقائيًا بآخر نجاح وآخر فشل لكل suite، وعدم التخمين من اسم المجلد.
3. عدم حذف VM أو archive أو database إلا بخيار صريح منفصل وبعد تحقق target داخل workspace.
4. استثناء `.git` وVM وreparse points من المسح المكلف، مع manifest دقيق للأهداف المحذوفة.
5. حذف الأدلة القديمة فقط بعد استخراج summary غير حساس؛ البيانات الخام تبقى محلية.

نسخة VM الحالية (نحو 89.32GB) لا تُحذف ضمن التنظيف الآلي. قرارها مستقل بعد اكتمال قبول الإصدار.

## 12. تعريف إغلاق أي عيب

لا يعتبر العيب محلولًا إلا إذا توفر الآتي:

1. وصف قابل لإعادة الإنتاج ودرجة P0–P3.
2. سبب جذري، وليس معالجة للعرض فقط.
3. اختبار يفشل قبل الإصلاح وينجح بعده.
4. إصلاح محدود لا يوسع الصلاحيات أو مسارات الحذف.
5. كل بوابات المجال والبناء العام ناجحة بلا warnings.
6. تحديث changelog/docs عند تغير السلوك أو التشغيل.
7. دليل منقح محفوظ، وخطة rollback معروفة.

## 13. تعريف اكتمال المشروع للإصدار

- لا P0/P1 معروفة أو مؤجلة.
- كل الاختبارات الحالية والجديدة ناجحة على source وعلى الحزمة النهائية نفسها.
- صفر تحذيرات بناء، وصفر ثغرات High/Critical معروفة.
- VM matrix كاملة بمثبت موقع وSHA256/SBOM محفوظين.
- ميزانيات startup/memory/bundle محققة، وتدقيق الوصول وRTL ناجح.
- النسخ الاحتياطي/الاستعادة/التنظيف مثبتة باختبارات failure injection.
- المثبّت النهائي فقط هو الذي يُرقّى داخل `dist`؛ حزم الاختبار تبقى في `_build` ثم تزال بعد حفظ summary.
